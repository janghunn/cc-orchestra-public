### 2026-10-07 — Claude Code mods: mechanics and an observe-only prototype

This task read that summary, not the branch diff. The post's own advice that permission rules are the hard block matches how `guardrails.json` already works here, so a mod enforcement layer would duplicate it unless it can see something hooks cannot. No concrete next step is known, so no separate "mods as enforcement" entry is added. Caveat: the task 66 summary says live runtime behaviour is still unverified (alias resolution in the spawn result, the spawn/step agentId join, profile effort reaching `turn.step`); one opt-in session with `claude --plugin-dir <repo>/mods/orch-spawn-observer` and a read of `spawn-observer.jsonl` would show it, and this task did not do that.

### 2026-10-07 — OpenRig: what it is and what was taken from it
- **Source:** https://github.com/mvschwarz/openrig (README via `gh api`, 2026-10-07; Apache-2.0, 5548 stars, last push 2026-10-07).
- **Summary:** OpenRig is a local daemon, CLI, terminal UI and MCP server on tmux that runs persistent multi-agent teams defined in a RigSpec YAML (pods, members, edges, continuity policies, a culture file). Its README has a table of what each phase writes on the machine and a `rig setup --dry-run`.
- **Critical assessment (cc-orchestra-specific):** The architecture differs: OpenRig runs long-lived peer seats you message (`rig send`, a queue), while this repo runs in-session hierarchical leads with evidence gates and a second provider as reviewer, so it is not adoptable wholesale. The install-transparency idea is the part tied to a gap here and is task 65 (branch `orch/65-install-dry-run`, in flight; its outcome was not read). Ideas judged not applicable: the typing guard (`rig seat set-typing-guard`) holds automatic messages for a seat a human types into, but cc-orch leads are subagents of one session with no hand-typed seats; `CULTURE.md` resembles `.orchestra/DIRECTIVES.md` only loosely, since DIRECTIVES holds the user's dated standing directives and OpenRig's culture file holds coordination norms, which here live in agent prompts, so no concrete gap is shown. Caveat: the README was read, not the code, and the star count is a snapshot.
- **Status:** USER APPROVED — see orch/65

### 2026-10-07 — Vocabulary for the outcome of resuming a lead after interruption
- **Source:** https://github.com/mvschwarz/openrig README, section on snapshot/restore (fetched 2026-10-07); this repo's `agents/orchestrator.md` (REGISTRY, agentId routing) and `OPERATIONS.md` ("Compaction recovery hook").
- **Summary:** OpenRig's restore reports a per-node outcome: `resumed`, `fresh-primed`, `awaiting-decision` (the original conversation cannot resume; choose `--fresh`), `attention_required` or `failed`. Here, Tier 1 resumes a lead by looking up its agentId in `.orchestra/REGISTRY.md` and sending to it, and the compaction hook re-injects registry rows, the slot board and `DIRECTIVES.md`.
- **Critical assessment (cc-orchestra-specific):** The registry has a `status` column (`RUNNING`, `PASS`, `FAIL`, `BLOCKED`, `ACCEPTED`, `CLOSED`) but no field says whether a lead was resumed with its context, replaced by a fresh agent, or is waiting on a decision after a failed resume. That distinction would matter when a lead's agentId is stale. How often that happens here is not measured, and this task did not search past summaries for such cases. Caveat: OpenRig restores tmux processes; here the outcome after a failed resume is not recorded, so only the vocabulary transfers, not the mechanism. A name-addressed send that fails (`agents/orchestrator.md`) is a recoverable routing error, not lost context, and would need its own outcome.
- **Status:** NEW
